# 報告文

人に返す報告、障害連絡、進捗共有、レビュー結果に適用する。

読み手は作業の途中にいる。最初に必要とするのは、結果、影響、未決のこと、次の行動である。該当するものを先に示す。

## 書く順序

```
1. 入力にある事実だけを箇条書きで並べる
2. そのうち、読み手が判断に使うものを選ぶ
3. 選んだものを一文にまとめ、先頭に置く
4. 残りを本文に書く
5. 送る前の点検を通す
```

手順1で並べたものの外に出ない。手順4で書き足したくなったら、それが入力にあるかを確かめる。

## 確かめていないことを書かない

渡された情報の外にあることを、事実として書かない。原因、影響、安全性、競合の有無を、確かめずに書かない。読み手はそれを検証せずに信じる。

書いてよいのは次の三つ。

- 入力にある事実
- 入力から論理的に導ける結論。導出の根拠を添える
- 推測であると明示したもの。何を確かめれば決まるかを添える

例を挙げる。「バッチ処理は毎時実行される」が入力にあるとき、「削除は最大1時間遅れる」は導ける。「タイミングによる競合は発生しない」は導けない。競合の有無は入力にない。

## 結論を最初の一文に置く

経緯から書き始めない。何を観測し、何が変わり、何が未決かを先に出す。経緯が必要なら結論の後に置く。

判断を求めない共有だけの報告もある。その場合は、何が変わったかを先頭に置く。

これから書くことの予告を先頭に置かない。「以下に〜を示す」「〜について報告する」で始めず、一文目から報告を始める。

## 強調を絞る

強調が何箇所も出ると、どの文も同じ重さに見え、強調が働かなくなる。

読み手が判断を求められる一点と、方針が変わった一点。この二つに絞るのが目安である。それ以上を強調したくなったら、順序で示す。重いものを先に置く。

障害報告のように長く、複数の段に分かれる文書では、見出しや複数の強調が要ることもある。二箇所は絶対の上限ではない。

## 報告で壊れやすい形

| 出た形 | 直した形 |
|---|---|
| 障害発生時の影響範囲特定手順の整備 | 障害が起きたとき、どこまで影響するかを調べる手順を整える |
| 現状は改善傾向にあるものの継続的な監視が必要 | エラーは日に3件まで減った。原因は分かっていない |

長い報告には先頭に要約を置く。要約に専門用語を詰めない。要約だけ読んで判断できる状態にする。

## 送る前に見るもの

- 書いた事実は、すべて入力にあるか
- 最初の一文は結論か。予告になっていないか
- 推測を推測として書いたか。根拠を示したか
- 一文一義になっているか
- 名詞が四つ以上つながっていないか
- 強調が多すぎないか
- 長いなら先頭に要約があるか
- 同じ対象を複数の語で呼んでいないか
