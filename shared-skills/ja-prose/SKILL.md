# ja-prose — 技術文書のリズムと論理密度

論文草稿、設計文書、README、仕様書など、人が読む技術文書全般に適用する。
規則を一つずつ当てはめた継ぎはぎではなく、文脈が自然につながり、読み手が一度で論理を追える日本語を書く。

次の規則は `ja-writing-rules` スキルの SKILL.md と `reference/` が決める。ここには書かない。

| 規則 | 正本 |
|---|---|
| 擬人化、直訳の慣用句、話し言葉の動詞を、起きることの語に直す | SKILL.md「起きることを語で書く」 |
| 二重否定と否定を含む条件を、真偽を保って畳む | SKILL.md「否定と条件を畳むときは真偽を保つ」 |
| 文書そのものについて述べる文、飾り、打ち消しを添えた対比、予防線を削る | SKILL.md「中身のない文と語を削る」 |
| 能動態を優先する。動詞を名詞化しない。名詞の連鎖を動詞に開く | SKILL.md の各節 |
| 渡されていない事実・数値を補わない | SKILL.md「確かめていないことを書かない」 |
| 直すときに確信の度合い、数、主張の重さ、構成を変えない。意味が決まらなければ問う | `reference/revising.md` |
| 因果、例の範囲、譲歩、先送りした話を点検する | `reference/argument.md` |
| 強調 (太字) を絞る | `reference/reports.md`「強調を絞る」 |

## 原則

1. **適切な論理密度を保つ (細切れにしない)**:
   - 一文一義を、文を機械的に割る規則として読まない。数えるのは書いた主張の数である。
   - 前提の範囲、境界条件、否定、帰結が一つの主張に属するなら、自然な複文として一文にまとめる。
   - 長い複文が続いた後は、短い文で論点を着地させる。ただし、リズムのためだけに短い文を差し込まない。
2. **文の長さと読点は点検の合図にとどめる**:
   - 一文30〜45字、読点0〜2個は、点検を始める合図であって規則ではない。`ja-writing-rules` は字数や語数で判定しない。
   - 60字を超える文や読点が3個以上の文に出会ったら、主述と修飾の係り受けを点検して整理する。
   - 並列の関係がはっきりしているときだけ箇条書きにする。コロン見出しの箇条書きを乱用しない。
3. **機械的な禁止パズルを避ける**:
   - 「である」の連続や体言止めを避けるために、不自然な接続詞やゆがんだ言い換えを挟まない。疑問形や体言止めを、語尾を散らす手段として入れない。論理の流れに沿って素直に述語を選ぶ。
4. **シングルパス執筆**:
   - 通常のターンでは、段落の密度を測る、grep で文末を数えるといった自己ループを回さず、最初から良い型で書く。
   - 検査スクリプトは、推敲を頼まれたときと、既存の文書を直すときに使う。下記の「推敲の手順」に従う。

## 具体例 (Before / After)

### 例 1: 細切れの羅列をまとめる
- **Bad**: 本手法は屋外環境を対象とする。ただし夜間は対象外である。また動体が多く存在する環境では誤差が増加する。そのため静的な昼間シーンで評価を行った。
- **Good**: 本手法は屋外の静的な昼間環境を対象としており、動体が多い環境や夜間条件は評価対象から除外した。

### 例 2: 文長と読点を整理する
- **Bad**: 本処理系においては、入力データの検証を厳密に行うため、異常値を検知した際には、即座に例外を送出し、処理を中断して、ログに記録する。
- **Good**: 本処理系は入力データを厳密に検証する。異常値を検知したときは即座に例外を送出して処理を中断し、ログを記録する。

起きることの語への直し方と、意味が決まらないときの問い方の例は、それぞれの正本 (SKILL.md、`reference/revising.md`) にある。

## 推敲の手順

人の文書を直すときは、この順で進める。

1. 直す前に読み、書き手の主張と、その重さの順を控える。
2. `reference/revising.md` の「直すときに変えないもの」を守って直す。論文の草稿と設計文書では、`reference/argument.md` で論証も点検する。論証の欠けは補わずに書き手に伝える。
3. 直したあと、`reference/revising.md` の「直したあとに確かめること」を通す。検査スクリプトが入っていれば、下記の手順で機械的にも確かめる。

## 検査スクリプトの使い方

検査スクリプトはこのリポジトリに含めない。外部の次の二つが持つ (どちらも MIT License)。役割が違うので、入っているものはすべて使う。片方だけなら、その手順だけを行う。

| スクリプト | 何を見るか |
|---|---|
| [natural-japanese](https://github.com/coji/natural-japanese) の `lint.py` | AI が書いた日本語に出やすい型。人と AI の文書で閾値を校正してある。前回の結果と比べられる |
| natural-japanese の `calques.py` | 「起きることを語で書く」に当たる語の候補 |
| [yomiyasu](https://github.com/nanaism/yomiyasu) の `yomiyasu_diff.py` | 直す前と後の差。否定の反転、数値、慎重な言い方が減ったこと、引用の変化 |
| natural-japanese の `newfacts.py` | 直した後にだけある数値・固有名詞。yomiyasu がないときの代わり。確信の度合いの変化は見ない |

natural-japanese はスキルとして有効にしない。この規約と違う指示が同時に読まれるためである。clone して `skills/natural-japanese/scripts/` だけを使う。これらは uv で動き、初回に形態素解析の辞書を取得する。以下の `<nj>` はその `scripts/` を、`<yomiyasu>` は yomiyasu の `skills/yomiyasu/scripts/` を指す。

1. 直す前: `uv run <nj>/lint.py --genre tech --json <対象> > <一時ディレクトリ>/before.json`
2. 直した後:
   - `uv run <nj>/lint.py --genre tech --baseline <一時ディレクトリ>/before.json <対象>` で、新しく出た指摘と残った指摘を見る
   - `uv run <nj>/calques.py <対象>` で、言い直す語の候補を見る
   - `python3 <yomiyasu>/yomiyasu_diff.py <原文> <直した文>` で、意味が変わる恐れのある箇所を見る。yomiyasu がなければ `uv run <nj>/newfacts.py --git <対象>` で代える
3. どの指摘も確かめる場所であって、判定ではない。直すかどうかは規約に照らして決める。

どちらも入っていないときは、この手順を飛ばし、飛ばしたことを報告に書く。
