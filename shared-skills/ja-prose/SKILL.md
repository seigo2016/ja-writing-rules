# ja-prose — 技術文書のリズムと論理密度

論文草稿、設計文書、README、仕様書など、人が読む技術文書全般に適用する。
ルール遵守のための機械的なパッチワークではなく、文脈が自然に繋がり、読み手が一度で論理を把握できる日本語を書く。

次の規則は `ja-writing-rules` スキルの SKILL.md と `reference/` が決める。ここには書かない。

| 規則 | 正本 |
|---|---|
| 文書そのものを実況・予告する文を削る | SKILL.md「文書構造をなぞるだけの文を削る」 |
| 能動態を優先する。動詞を名詞化しない | SKILL.md「能動態を優先する」「動詞を名詞に変えない」 |
| 名詞の連鎖を動詞に開く | SKILL.md「名詞の連鎖を動詞に開く」 |
| 渡されていない事実・数値を補わない | SKILL.md「確かめていないことを書かない」 |
| 強調 (太字) を絞る | `reference/reports.md`「強調を絞る」 |

## 原則

1. **適切な論理密度を保つ (過剰な細切れの禁止)**:
   - 一文一義を、文を機械的に割る規則として読まない。数えるのは書いた主張の数である。
   - 前提範囲、境界条件、否定、帰結が一つの主張に属するなら、自然な複文として1文にまとめる。
   - 長い複文が続いた後は、短い文で論点を着地させる。
2. **文の長さと読点は点検の目安にとどめる**:
   - 1文30〜45字、読点0〜2個は、点検を始める合図であって規則ではない。`ja-writing-rules` は語数で判定しない。
   - 60字超の文や読点3個以上の文に出会ったら、主述と修飾の係り受けを点検して整理する。
   - 並列関係が明確な場合のみ箇条書きにする。コロン見出しの箇条書きを乱用しない。
3. **擬人化と比喩動詞の整理**:
   - 道具や概念に感情・意志を持たせる擬人化 (「ログが訴える」「関数が嫌がる」) を解消する。ただしツールの客観的機能記述 (「ツールがログを収集する」) は残す。
   - 「倒す」「効く」「溶かす」「潰す」等の比喩動詞は、文脈に合った平易な具体語 (「解決する」「対応する」) に改める。元のニュアンスや含みは損なわない。
4. **意味が確定しないときは書き手に問う**:
   - 主語や係り受けが曖昧で文の意味が確定しない場合は、勝手に補完して書き換えない。原文を維持し、確認の問いを返す。
5. **機械的な禁止パズルを避ける**:
   - 「である」の連続や体言止めを避けるために不自然な接続詞や歪な言い換えを挟まない。論理の流れに沿って素直に述語を選ぶ。
6. **シングルパス執筆**:
   - 通常のターンでは、段落密度の計測や grep による文末カウントなどの自己ループを回さず、最初から良い型で出力する。
   - 検査スクリプトは、推敲を頼まれたときと、既存の文書を直すときに使う。下記の「検査スクリプトの使い方」に従う。

## 具体例 (Before / After)

### 例 1: 羅列 (過剰な細切れ) の解消
- **Bad**: 本手法は屋外環境を対象とする。ただし夜間は対象外である。また動体が多く存在する環境では誤差が増加する。そのため静的な昼間シーンで評価を行った。
- **Good**: 本手法は屋外の静的な昼間環境を対象としており、動体が多い環境や夜間条件は評価対象から除外した。

### 例 2: 擬人化と比喩動詞の平易化
- **Bad**: 新しいアルゴリズムが例外を倒し、システムが安定を祈りながらログを吐き出す。
- **Good**: 新しいアルゴリズムで例外を処理し、システムがログを順次出力する。

### 例 3: 文長・読点の整理
- **Bad**: 本処理系においては、入力データの検証を厳密に行うため、異常値を検知した際には、即座に例外を送出し、処理を中断して、ログに記録する。
- **Good**: 本処理系は入力データを厳密に検証する。異常値を検知したときは即座に例外を送出して処理を中断し、ログを記録する。

### 例 4: 意味未確定時の著者への確認
- **Bad**: (意味が曖昧な文に対して推測で補完) 「取込処理では重複を避けるため、キーを登録してから書き込む。」→「取込処理はデータベースに一意キーを登録してから書き込む。」(キーの登録先を確かめないまま断定)
- **Good**: (原文を保持して確認) キーの登録先がデータベースか処理内の一時的な表かを文から確定できないため原文を維持し、書き手に「キーはどこに登録しますか」と問いを返す。

## 検査スクリプトの使い方
検査スクリプトはこのリポジトリに含めない。外部の [yomiyasu](https://github.com/nanaism/yomiyasu) プラグイン (MIT License) の `yomiyasu` スキルが持つ。

- `yomiyasu` スキルが入っているときは、そのスキルのディレクトリにある `scripts/` を使う。
  - 推敲の前後で `python3 <yomiyasu スキル>/scripts/yomiyasu_lint.py <対象ファイル>` を実行し、指摘件数の増減を比較する。
  - `python3 <yomiyasu スキル>/scripts/yomiyasu_diff.py <原文> <推敲後>` を実行し、意味の変質や情報欠落の恐れがある箇所を確認する。
- 入っていないときは、この手順を飛ばす。飛ばしたことを報告に書く。

日本語 AI 表現の一覧や文書種別ごとの基準も yomiyasu スキルの `references/` にある。原則 2〜4 の目安と考え方は yomiyasu を参考にした。
