# ja-writing-rules — 読み手が一度で受け取れる日本語

報告文と命名は下記の参照先に詳しい。この SKILL.md と `reference/` が、共通の規則の正本である。文のリズムの規則は `ja-prose`、英語の型の規則は `slop-removal` が正本を持つ。`ja-naming`、`ja-report`、`ja-prose`、`slop-removal` はここにある規則を再掲せず参照する。

## 適用しない場所

- 引用文。原文のまま残す
- 法令・契約・規格の定型表現
- コード識別子、API 名、コマンド、設定キー
- 既存 UI の固定ラベル
- 忠実さを優先する翻訳
- 利用者が文体を指定した場合。指定が優先する

## 最初に読み手を決める

読み手によって、専門用語を残すか説明するかが変わる。読み手が専門家なら専門用語を削って冗長な言い換えに置き換える方が読みにくい。

## どこを読むか

| 書くもの | 参照先 |

| 人に返す報告、障害連絡、進捗共有 | [reference/reports.md](reference/reports.md) |
| 日本語で名前を決める、訳語を選ぶ | [reference/naming.md](reference/naming.md) |

## 共通ルール

### 確かめていないことを書かない

渡された情報の外にあることを、事実として書かない。確かめていない原因、影響、安全性、競合の有無を書かない。読み手はそれを検証せずに信じる。

入力から論理的に導ける結論は書いてよい。導出の根拠を添える。推測を書くなら推測だと示し、何を確かめれば決まるかを添える。

人の文書を直すときは、確信の度合い、数、主張の重さも変えない。規則は [reference/revising.md](reference/revising.md) にある。

### 一文一義で書く

一つの文に一つのことだけを書く。数えるのは文の長さではない。書いたことの数を数える。接続助詞でつなぐと、一文に複数のことが入りやすい。

### 語をそろえる

一つの文書のなかで、同じ対象を複数の語で呼ばない。書き終えたら中心になる対象ごとに語を検索して揺れをなくす。

検査の範囲には、上流の文書と、既に相手へ送った文書も含める。

一つの語を一つの品詞で使う。日本語は「する」を付けるだけで名詞が動詞になるため、「閾値する」の形を作らない。

### 決まった語を動かさない

相手に送ったメール・資料・仕様書で使った語は、既に相手の手元にある。後から変えると、相手のなかで別の概念になる。文体を整えるために変えない。変えるなら明示して伝える。

仕様書や相手が使った語を、別の概念語に置き換えない。言い換えるなら理由と対応を書いてから行う。

規約が衝突したときの順序は次の通り。

1. 相手に送った語と形
2. 同じ主題で既に書かれた文書
3. その現場の慣行
4. 一般の文章規約

### 能動態を優先する

誰が何をするか、誰に責任があるかを示す必要がある文では、能動態を使う。

対象や結果を主題にしたい場合、行為者が重要でない場合、システムの動作として行為者を書かない方が自然な場合は、受動態でよい。

### 起きることを語で書く

読み手が字義どおりに受け取れない語を使うと、何が起きるかが文から読み取れない。次の四つの型に出やすい。

- 擬人化: 「ログが訴える」「関数が嫌がる」。道具の機能をそのまま書く「ツールがログを集める」は擬人化ではない
- 英語の慣用句の直訳: 「価値を運ぶ」「開かれた問題」「リスクに晒す」
- 話し言葉の動詞: 「効く」「刺さる」「吐く」「投げる」「倒す」
- 名前のあるものの言い直し: 既に名前のある手法や状態を、その場で作った呼び名で呼ぶ

迷ったら二段で確かめる。まず、その語の字義どおりの動作を思い浮かべられるか。浮かぶなら比喩を疑う。次に、主体と対象を具体的な語に置き換えて言い直せるか。言い直せた文が書くべき文である。

| 出た形 | 直した形 |
|---|---|
| 新しい検証がこの不具合に効く | 新しい検証は、この入力の組み合わせを拒否する |
| キャッシュがリクエストを吸収する | 同じリクエストはキャッシュから返し、サーバに届かない |

「解決する」「対応する」「処理する」のような意味の広い漢語に置き換えて済ませない。中身が見えないことは変わらない。言い直せないなら、その文はまだ主張になっていない。人の文書を直しているなら、書き手に何を指すかを問う。

手順や仕組みも、起きることで書く。「〜するだけでよい」「〜しなくてよい」「〜してよい」と許可の形で結果だけを言うと、なぜそれで済むのかが読み手に見えない。何をすると何が起きるか、なぜそうなるかを書く。規約が規則として許すこと (「受動態でよい」など) は、許可の形のまま書く。

| 出た形 | 直した形 |
|---|---|
| 更新はクローンで git pull するだけでよい。利用側は何も変えなくてよい | 規約を更新するには、クローンで git pull を実行する。利用側はクローンへのリンクを持つので、そのまま新しい規約を読む |

### 否定と条件を畳むときは真偽を保つ

二重否定と、否定を含む条件は、肯定の形に畳むと読みやすくなる。畳んだら、元と同じ場合に真になるかを確かめる。

- 「増えないとは言えない」は「増えることがある」であって、「増えない」ではない
- 「無効でない限り」と「有効なら」は、値が設定されていないときの扱いが違うことがある

控えめに肯定する言い方が書き手の意図なら残す。統計の検定の結論 (「帰無仮説を棄却できない」) は畳まない。

### 動詞を名詞に変えない

「検討を行う」ではなく「検討する」。「〜の実施」ではなく「〜する」。動詞を名詞の形にすると、誰が何をするのかが文から消える。

### 名詞の連鎖を動詞に開く

名詞が長く連なり、要素どうしの関係が文から読めないなら、動詞に開く。「の」でつないだ連なりも含む。

| 出た形 | 直した形 |
|---|---|
| 認証トークン検証処理の並列化 | 認証トークンの検証を並列に実行する |
| 設定ファイル読み込みエラー発生時の再試行制御 | 設定ファイルの読み込みに失敗したとき、再試行する |

分解するのは、専門用語をつなぐ「の」と、動詞を名詞の形にした部分である。専門用語そのものは分解しない。

動詞に開くと、要素どうしの関係を書かざるを得なくなる。名詞の連鎖のままでは、主張の構造が読み手に見えない。

### 一つの段落に一つの話題

話題が変わったら段落を変える。語数では分けない。

### 中身のない文と語を削る

削っても言っていることが変わらない文と語は、読み手の手間だけを増やす。次の四つの形に出やすい。

- 文書そのものについて述べる文: 「本節では〜を扱う」「以下に〜を示す」「以上のように」。短い断定に整えると要点に見えるため、気づかれずに残りやすい
- 中身を足さない飾り: 「重要なのは」「正面から」「包括的な」「掘り下げる」。姿勢や重さを示すだけで、何が重要で何を調べたのかを書いていない
- 打ち消しを添えた対比: 「A ではなく B である」「B であって A ではない」「A は B ではない。C だ」。打ち消された A は、読み手が考えてもいない選択肢であることが多い。B だけを書く
- 予防線: 書いた規則や主張を、すぐあとで弱める文。「〜は目安であって上限ではない」「〜とは限らない」「〜することもある」

直し方は削ることである。言い換えて補わない。言い換えると、元になかった調子や決め台詞が入る。

打ち消しを残すのは、直前の文や文書の文脈から、読み手がその誤りに実際に進むと言えるときだけである。規則の適用の範囲も、打ち消しで示さず、何に使うかを肯定の形で書く。「この一覧は、点検する場所を見つけるために使う」のように書く。長い仕様書で節の目的や前提を示す案内文は、中身として残す。

## 症状から引く

| 症状 | 直し方 |
|---|---|
| 何を言いたいか最後まで分からない | 結論を最初の一文に出す |
| どこが重要か分からない | 強調を絞り、残りは順序で示す |
| 一文を二度読む必要がある | 一文一義にする |
| 内容が薄く感じる | 中身のない文と語を削る |
| 何が起きるのか分からない | 起きることを語で書く |
| 否定が重なって真偽が取りにくい | 否定と条件を畳み、真偽を確かめる |
| 主張が根拠より広く聞こえる | [reference/argument.md](reference/argument.md) で主張と根拠を突き合わせる |
| 直したら書き手の言いたいことが変わった | [reference/revising.md](reference/revising.md) の「直すときに変えないもの」を見る |
| 硬く意味が取りにくい | 名詞の連鎖を動詞に開く |
| 誰がやるのか分からない | 能動態に戻し、動詞を動詞のまま書く |
| 同じものを指すか確信が持てない | 対象ごとに検索して一語に統一する |
| 読み手が判断できない | 観測と推測の境界を文の形で示す |
