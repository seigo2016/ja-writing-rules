# ja-writing-rules — 読み手が一度で受け取れる日本語

報告文と命名は下記の参照先に詳しい。この SKILL.md と `reference/` が、各規則の正本である。`ja-naming`、`ja-report`、`ja-prose`、`slop-removal` は、ここにある規則を再掲せず参照する。

## 適用しない場所

- 引用文。原文のまま残す
- 法令・契約・規格の定型表現
- コード識別子、API 名、コマンド、設定キー
- 既存 UI の固定ラベル
- 学術論文。論文の草稿は `ja-prose` と `slop-removal` を使う
- 忠実さを優先する翻訳
- 利用者が文体を指定した場合。指定が優先する

## 最初に読み手を決める

読み手によって、専門用語を残すか説明するかが変わる。読み手が専門家なら専門用語を削って冗長な言い換えに置き換える方が読みにくい。

## どこを読むか

| 書くもの | 参照先 |
|---|---|
| 人に返す報告、障害連絡、進捗共有 | [reference/reports.md](reference/reports.md) |
| 日本語で名前を決める、訳語を選ぶ | [reference/naming.md](reference/naming.md) |
| README、設計文書、仕様書、通知文 | 下記の共通ルール |
| 文のリズム、擬人化・比喩動詞の整理、論文・技術文書の推敲 | `ja-prose` スキル |
| AI 生成文に出る型の除去 | `slop-removal` スキル |
| 検査規則 (ja-lint) の追加と見直し | `ja-lint-rules` スキル |

## 共通ルール

### 確かめていないことを書かない

渡された情報の外にあることを、事実として書かない。原因、影響、安全性、競合の有無を、確かめずに書かない。読み手はそれを検証せずに信じる。

入力から論理的に導ける結論は書いてよい。導出の根拠を添える。推測を書くなら推測だと示し、何を確かめれば決まるかを添える。

### 一文一義で書く

一つの文に一つのことだけを書く。数えるのは文の長さではない。書いたことの数を数える。接続助詞でつなぐと、一文に複数のことが入りやすい。

### 語をそろえる

一つの文書のなかで、同じ対象を複数の語で呼ばない。書き終えたら中心になる対象ごとに語を検索して揺れをなくす。

検査の範囲は一つの文書に閉じない。上流の文書と、既に相手へ送った文書も含めて照合する。

一つの語を一つの品詞で使う。日本語は「する」を付けると名詞が動詞に滑るため、「閾値する」の形を作らない。

### 決まった語を動かさない

相手に送ったメール・資料・仕様書で使った語は、既に相手の手元にある。後から変えると、相手のなかで別の概念になる。文体を整えるために変えない。変えるなら明示して伝える。

仕様書や相手が使った語を、別の概念語に置き換えない。言い換えるなら理由と対応を書いてから行う。

規約が衝突したときの順序は次の通り。

1. 相手に送った語と形
2. 同じ主題で既に書かれた文書
3. その現場の慣行
4. 一般の文章規約

規約に書かれた数値は目安であって上限ではない。

### 能動態を優先する

誰が何をするか、誰に責任があるかを示す必要がある文では、能動態を使う。

対象や結果を主題にしたい場合、行為者が重要でない場合、システムの動作として行為者を書かない方が自然な場合は、受動態でよい。

### 動詞を名詞に変えない

「検討を行う」ではなく「検討する」。「〜の実施」ではなく「〜する」。動詞が名詞に化けると、誰が何をするのかが文から消える。

### 名詞の連鎖を動詞に開く

主語から述語までに名詞が四つ以上並んでいたら、書き直しを検討する。四つは目安であって上限ではない。

| 出た形 | 直した形 |
|---|---|
| 認証トークン検証処理の並列化 | 認証トークンの検証を並列に実行する |
| 設定ファイル読み込みエラー発生時の再試行制御 | 設定ファイルの読み込みに失敗したとき、再試行する |

分解するのは、専門用語をつなぐ「の」と、動詞から名詞に化けた部分である。専門用語そのものは分解しない。

動詞に開くと、要素どうしの関係を書かざるを得なくなる。名詞の連鎖は主張の構造を隠す。

### 一つの段落に一つの話題

話題が変わったら段落を変える。語数では分けない。

### 文書構造をなぞるだけの文を削る

「本節では〜を扱う」の形の文は、文書そのものについて述べている。削って前後がつながるならその文は要らなかった。整えて短い断定にすると要点のように見えるため、いちばん気づかれずに残る。

残すのは、節の目的や前提、他の節との関係を示す案内文。長い仕様書では読み手の位置把握を助ける。削るのは文の形であって、内容ではない。

## 症状から引く

| 症状 | 直し方 |
|---|---|
| 何を言いたいか最後まで分からない | 結論を最初の一文に出す |
| どこが重要か分からない | 強調を絞り、残りは順序で示す |
| 一文を二度読む必要がある | 一文一義にする |
| 内容が薄く感じる | 文書構造をなぞる文を削る |
| 硬く意味が取りにくい | 名詞の連鎖を動詞に開く |
| 誰がやるのか分からない | 能動態に戻し、動詞を動詞のまま書く |
| 同じものを指すか確信が持てない | 対象ごとに検索して一語に統一する |
| 読み手が判断できない | 観測と推測の境界を文の形で示す |

## 参考にした資料

以下の考え方を参考にした。

- [Federal Plain Language Guidelines](https://www.plainlanguage.gov/guidelines/) (米国、2011年)。根拠法は [Plain Writing Act of 2010](https://www.govinfo.gov/content/pkg/PLAW-111publ274/pdf/PLAW-111publ274.pdf)。能動態、動詞の名詞化、段落の長さ、読み手の知識に合わせることを扱う
- [W3C COGA — Making Content Usable for People with Cognitive and Learning Disabilities](https://www.w3.org/TR/coga-usable/)。平易な語、長い文書の要約、新しい語を作らないことを扱う
- [WCAG 2.1](https://www.w3.org/TR/WCAG21/)。読解水準と、珍しい語・略語の説明に関する達成基準
