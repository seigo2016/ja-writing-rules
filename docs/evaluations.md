# 評価

規約とスキルの効き目を、Claude に実際のタスクを与えて測った記録。新しい評価を先に、規約の対象を移す前の評価を後に置く。

## 2026-11-20 の評価

### 方法

道具は [evals/](../evals/) にあり、同じ手順で測り直せる (`python3 evals/run.py --out <dir>` のあと `python3 evals/score.py --out <dir>`)。

- タスクは五つ。設計文書の一節を書く、研究の記録の段落を書く、共同研究者への報告を書く、下書きを直す、直してはいけない部分を見分けて直す。下書きには、予告、比喩、予防線、打ち消しを添えた対比、二重否定、残すべき推量、数値を仕込んだ
- 条件は二つ。スキルなしは空のプロジェクト、スキルありは `init.py apply` で登録したプロジェクトで、検査フックも動く (35 回すべてで動いた)。どちらも `--setting-sources project,local` で起動し、利用者の普段のプラグインを外した。利用者の CLAUDE.md はどちらの条件でも読まれる
- モデルと回数: Sonnet と Opus を各 3 回、Haiku を 1 回。条件ごとに 35 回、計 70 回
- 採点は二つ。機械の検査 (仕込んだ問題が消えたか、残すべきものが残ったか、入力にない数値が出たか) と、条件を伏せた Opus による 6 項目の採点 (R1 入力にない事実を足さない、R2 確かめていないことを推測や未確認と分かる形で書く、R3 最初の文が要点、R4 中身のない文がない、R5 比喩で中身を隠さない、R6 一文一義と名詞の連鎖)

### 結果

項目ごとの通過率 (条件ごとに全タスク・全モデルを合わせた値)。

| 項目 | スキルなし | スキルあり |
|---|---|---|
| R4 中身のない文がない | 0.69 | 0.94 |
| R2 確かめていないことの書き方 | 0.80 | 0.97 |
| R3 最初の文が要点 (書くタスクのみ) | 0.71 | 0.81 |
| R1 入力にない事実を足さない | 0.97 | 0.91 |
| R5、R6 | 1.00 | 1.00 |
| 下書きの「本節では」を消した | 0.00 | 1.00 |
| 下書きの「魔法ではなく」を消した | 0.86 | 1.00 |
| 下書きの「効いた」を消した | 0.86 | 0.86 |
| 規約の引用を変えずに残した | 0.71 | 1.00 |
| 人の言葉の引用を変えずに残した | 0.86 | 1.00 |
| 推量と数値と二重否定の真偽を保った | 1.00 | 1.00 |

最も差が出たのは、中身のない文の削除と、確かめていないことの書き方だった。

### 読み方の注意

- R1 はスキルありのほうが低い。落ちた 3 回のうち 2 回は報告のタスクで、入力にない今後の手順 (「了承が得られれば適用し、再発するかを確かめます」) を足した。報告の規則が「次の行動」を先に示すよう求めているため、入力にない行動まで書いた可能性がある (推測)。もう 1 回は、設計文書で推論を言い切ったものである
- 機械の検査の「入力にない数値」は粗い。スキルなしで落ちたものの多くは手順の番号 (1. 2. 3.) で、スキルありで落ちた 4 回は、二つの値の差 (0.61 − 0.42 = 0.19) を書いたものだった。入力から導ける値なので、規約の上では書いてよい
- Haiku は各 1 回なので、モデルの違いはこの数からは言えない
- 「効いた」は、どちらの条件でも 7 回中 1 回残った
- R1 の落ちを受けて、報告の規則の「次の行動」を「読み手に頼むこと」に置き換えた。報告のタスクだけを同じ規模で測り直すと、今後の手順を足した出力はなくなった。R1 は 4/7 で、落ちたのは入力にない理由を足したもの、観測の範囲を広げたもの、推測と示して原因を書いたものだった。最後のものは規約では書いてよく、採点の R1 が規約より厳しい。採点の基準は、次に全体を測り直すときに規約に合わせる

## 2026-11 以前の評価 (対象を移す前)

規約の対象にエンジニアでない読み手への文書を含めていた時期の記録である。実行の回数は記録していない。


### 方法

同じタスクを、スキルなし (ベースライン) とスキルありで実行し、出力を比べた。
モデルは Sonnet。

タスクは三つ。エンジニアでない読み手への障害報告、実装者向けの設計文書、日本語の命名。
別に、適用除外が働くかを見るタスクを一つ用意した。

### 観測した差

| 観点 | スキルなし | スキルあり |
|---|---|---|
| 結論の位置 | 件名と事実の列挙が先 | 冒頭で判断が必要な点を示す |
| 推測の扱い | 与えていない推測を足した (「A社側に原因がある可能性が高い」) | 事実だけを書いた |
| 未検証の明示 | 「見込みですが」と断定に混ぜた | 「まだ検証していません」と分けた |
| 名詞の連鎖 | 失効済みセッションのレコードがストアに残存し得る | 削除前のレコードが残っていても認証には使われない |
| 命名の判断 | 社内文書との整合で決めた | 定着語の有無で決め、造語を避けた |

最も差が出たのは、観測と推測の分離だった。

### 適用除外の確認

法令の定型表現、エラーメッセージの定義、引用文、実装メモを混ぜた文書を渡した。

スキルありは四つを正しく区別した。法令・エラーメッセージ・引用文は無修正とし、実装メモだけを直した。クラス名とメソッド名は識別子として維持した。

### 見つけて直したもの

- 報告文の冒頭に予告を置く。「〜について報告する」から始めていた。予告を禁じる記述を追加した
- 短くする過程で、設計文書に必要な情報を落とした。「削るのは文の形であって内容ではない」を追加した

### モデル別の結果

Haiku、Sonnet、Opus で同じタスクを実行した。

Sonnet と Opus は規約に沿った。Opus は入力から導ける結論 (「削除は最大1時間遅れる」) と、入力にない事実を区別できた。過剰な説明にはならなかった。

Haiku は入力にない事実を書いた。「タイミングによる競合は発生しません」「遅い接続を早期に切ることになります」。いずれも渡していない情報である。

対処として、報告文に書く順序 (checklist) と「入力にない事実を書かない」を追加した。再テストで上記2件は消えたが、別の捏造が出た。「毎時0分に」(入力は「毎時」のみ)、「システムの動作に影響しません」。さらに、ユーザーが求めた選択肢を別のものに書き換えた。

### 制限

Haiku では、入力にない事実を書くことがある。規約を追加しても完全には直らなかった。

報告文と設計文書では、この失敗が読み手の判断や実装を直接誤らせる。Sonnet 以上を使うことを勧める。

規約をさらに強くする道はあるが、規約が長くなる代償に見合うかを確かめていない。

### 残っている挙動

作業の前置き (「規約を読んだ。3タスクを書く。」) は残る。ただしこれは成果物の外にある作業報告であり、規約の対象ではないと判断した。
